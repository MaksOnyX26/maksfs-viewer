## Совместимость и просмотр C++

- Общее изменение только в `indra/newview/app_settings/settings.xml`:
  автоматическое объединение сохранило оба независимых ключа. Все остальные
  файлы PR сохранены побайтно относительно соответствующего head.
- PR #1 меняет основной цикл, учёт FPS и жизненный цикл текстур; PR #2 — строку
  состояния, слушатель настройки и XUI. Новых пересекающихся объявлений,
  обработчиков или зависимостей между ними не обнаружено.
- `MaksFSFrameDiagnostics`: Boolean, Value=0, Persist=0.
  `MaksFSShowLocalTime`: Boolean, Value=1, Persist=1. Имена уникальны;
  диагностика выключена по умолчанию, местные часы включены.
- Проверены доступность публичных методов allocation counters, очередей и
  pending-флагов, область действия таймеров и последовательность очистки.
  Очередь downscale освобождается до основных списков; самостоятельный таймер
  сохраняет её прежний бюджет, общий таймер учитывает upload и downscale.
- Диагностика измеряет CPU wall time, включая намеренные sleeps; счётчики
  выделений не являются измерением всей RAM/VRAM. Она не покрывает весь `doFrame()`:
  работа до создания таймера и хвост после записи не входят в выборку.
- Местные часы используют OS wall clock, отдельный минутный кэш и существующий
  секундный tick; SLT сохраняет свой источник времени. Проверены объявления,
  подключение слушателя, инициализация контролов до первого обновления и пути
  видимости FPS/media/net stats/mouselook. Windows `localtime_s` и CRT `%z`
  требуют проверки на целевой платформе.
- Проект использует C++20; новых библиотек или изменений build profile нет.
  Статический просмотр не заменяет компиляцию translation units MSVC.

## Готовность GitHub Actions

Найден реальный блокер: `maksfs-build-windows.yml` разрешал job только для
`maksfs-main`. В интеграционной ветке внесена минимальная правка: разрешена
также **ровно** `codex/integration-pr1-pr2-20261110`. Остальные workflow и
скрипты CI не менялись. Нет push/PR триггера сборки; сохранение этой ветки
не запускает Windows-компиляцию автоматически.

Следующий ручной запуск после отдельного решения владельца:
Actions → **MaksFS first Windows build** → Run workflow → выбрать
`codex/integration-pr1-pr2-20261110` → `confirm_build=true`.
Нужно сверить head SHA с текущим head интеграционной ветки перед запуском
и с записанным `GITHUB_SHA` в identity/log после него.

Checkout получает выбранную ветку, без захардкоженного main ref. Job сам
подготавливает необходимые инструменты на новой машине; отдельный повторный
запуск environment/toolchain workflow не нужен. Сохранены VS2022, Python
3.11.9 x64, профиль ReleaseFS_open, x64, ограниченный параллелизм, проверки
CMakeCache, ручное подтверждение и лимит 150 минут. Проприетарные компоненты,
OpenSim, signing, installer и LL_TESTS отключены существующим профилем.

Runner `windows-2022` — Windows Server 2022, **не Windows 11**. Получается
кандидат Windows x64, который затем нужно отдельно проверить на Windows 11.
Этот workflow сохраняет только диагностические журналы на 7 дней: EXE,
portable и installer не выгружаются. Не следует менять его на packaging workflow
для этой проверки: packaging пытается использовать старые binaries с main и
при отличающихся C++/XML корректно откажет в их повторной упаковке.
Export workflow также выгружает старый фиксированный run, а не эту интеграцию.
Если нужен запускаемый тестовый дистрибутив, потребуется отдельно согласованный
этап сохранения/упаковки **новых** бинарников с проверкой SHA происхождения.

## Риски и проверки после компиляции

1. Ни один изменённый viewer translation unit здесь не скомпилирован.
   Нет подготовленного CMake build tree; MSVC, Windows SDK и PowerShell
   в текущей Linux-среде недоступны. Возможны ошибки Windows include/CRT,
   линковки или исходной версии, которых изолированный harness не выявляет.
2. Mutable runner image, SDK/MSVC и Cygwin mirror, внешние архивы зависимостей
   могут измениться. Закреплённый SHA256 Cygwin installer остановит установку
   при изменении установщика. Доступность всех архивов сейчас не проверялась
   загрузкой. Успех прошлой сборки не гарантирует успех новой.
3. Нужны runtime-проверки загрузки/завершения viewer и текстур под давлением
   памяти, reflections/snapshots, диагностики off/on. Прирост FPS и уменьшение
   памяти не измерены и не обещаются.
4. На Windows 11 проверить местные часы и UTC offset/DST, midnight, SLT,
   Cancel/Apply/restart, три skins, EN/RU, узкие окна/UI scaling,
   FPS/media/net stats/menu search/balance/Omnifilter и mouselook.
5. Целевой профиль без OpenSim и без FMOD/KDU/Havok не доказывает функциональную
   полноту Second Life/OpenSim или равенство официальному Firestorm.

`BUILDING.md` содержит исторический план первой сборки; фактические ограничения
этой интеграции и нужный ref описаны выше. Успешные прежние этапы не отменены.
После тестовой компиляции оба исходных PR следует сохранить Draft до необходимых
runtime-проверок. Временную ветку не сливать автоматически в `maksfs-main`.
