# MaksFS: аудит производительности и стабильности

Дата: 2026-11-10. Репозиторий: `MaksOnyX26/maksfs-viewer`.
Основа: `maksfs-main`, коммит `6dad28a7d853c29e1a477248c5ce47724b0cc327`.
Ветка изменений: `codex/maksfs-performance-audit`.

## Результат и границы проверки

Проведён статический аудит основного цикла, отображения, очередей текстур,
давления памяти, отражений и нескольких точек синхронизации с GPU.
Реализованы небольшие исправления времени жизни и учёта времени, локальное
сокращение числа выделений памяти и выключенная по умолчанию диагностика.
Рост FPS, уменьшение RAM/VRAM и устранение периодических просадок **не измерены**.
Конкретная причина наблюдаемых просадок без записи выполнения не установлена.
Перегрев ноутбука не является установленной причиной: температурных измерений
и данных о частотах/троттлинге в этом аудите нет.

Полная сборка, configure, загрузка SDK, установка зависимостей и запуск Actions
не выполнялись. Локальная копия получена shallow clone; история сервера сохранена.
Изменения сделаны в отдельной ветке; `maksfs-main` не изменялась.

## Подтверждённые по коду проблемы и изменения

| Участок | Наблюдение | Изменение и предел ожидаемого эффекта |
| --- | --- | --- |
| `LLViewerTextureList::shutdown()` | `mDownScaleQueue` содержит `LLPointer`, но в отличие от `mCreateTextureList` не очищалась. Оставшиеся записи удерживают текстуры после очистки основных списков, потенциально до разрушения глобального объекта. | Сброс `mDownScalePending` и освобождение очереди до очистки основных списков. Повторная очистка пустой очереди безопасна. Не выполняется обработка downscale; обычный цикл не затронут. Это исправление завершения работы, а не доказанная причина просадок во время сессии. |
| `updateImagesCreateTextures()` | Перед downscale сбрасывался общий таймер. При непустой очереди возвращаемое время не включало предыдущие upload-операции. | Отдельный локальный таймер downscale сохраняет прежний бюджет и аварийный минимум обработки; возвращаемое время включает обе стадии. Обычный `updateImages()` игнорирует результат, `decodeAllImages()` использует его только в debug-отчёте. Исправление точности, без заявлений об ускорении планировщика. |
| `display_stats()` | FPS вычислялся делением на константу 10 секунд, хотя фактический интервал мог быть длиннее. Например, 600 кадров за 12 секунд давали 60 вместо 50 FPS. | Деление на фактически прошедшее положительное время. Исправляется диагностическое завышение после задержек. |
| `decodeAllImages()` | Локальный вектор снимка списка заполнялся без резервирования, вызывая геометрические перераспределения буфера. | `reserve(mImageList.size())` перед заполнением. Сохраняются тип, владение и время жизни ссылок; новые постоянные буферы не вводятся. Эффект ограничен этим специальным путём, не обычным кадром. |

Сохранены лицензии и заголовки. Изменения помечены `FS:MaksFS`, исходные
заменённые выражения оставлены в комментариях по `CONTRIBUTING.md`.

## Возможные источники задержек: гипотезы, требующие измерения

| Участок | Статическое основание | Что измерять |
| --- | --- | --- |
| Давление RAM/VRAM | `LLViewerTexture::updateClass()` увеличивает discard bias; при первом серьёзном дефиците проходит по текстурам. `updateImagesFetchTextures()` увеличивает число обновлений при высоком bias. | Совпадение длинных кадров с ростом bias, allocation counters и очереди downscale; доступная физическая/commit-память по существующим средствам. Счётчики GL-выделений не равны общему потреблению VRAM. |
| Upload и downscale | `updateImagesCreateTextures()` выполняет GL-работу, бюджет проверяет между текстурами. Downscale имеет отдельный бюджет и обязательную обработку после его исчерпания. `updateImages()` оставляет каждой стадии минимальную долю времени. | Зоны Tracy, количество ожидающих текстур и время display. Один дорогой upload нельзя прервать проверкой бюджета между элементами. Урезать аварийный downscale без тестов опасно из-за нехватки памяти. |
| Очередь callbacks главного потока | `idle()` обслуживает `gMainloopWork.runFor(MainWorkTimeNanoSec)`. Бюджет очереди не прерывает уже исполняющийся callback. | `idle_mean_max_ms`, зоны `df idle`, длительности отдельных callbacks и ответы worker threads. |
| Отражения и снимки | После `display()` вызываются reflection manager и обновления снимков. Менеджер проходит по probes, сортирует их; `updateNeighbors()` ищет соседей в списке probes. Для большого числа обновляемых probes совокупная работа может значительно вырасти. | `post_display_mean_max_ms`, зоны `reflection manager update`, `rmmun - search`, динамические probes и перемещения камеры. Не менять порядок и бюджет probes без проверки картинки. |
| Намеренные ожидания | `doFrame()` содержит YieldTime, ожидание при потере фокуса, FPS limiter, сон при backlog LFS, тестовые random/periodic slow frame. | Сначала проверять настройки и состояние окна. `background` содержит и полезную работу texture/file/mesh, и sleep; сам по себе большой показатель не доказывает перегрузку рендера. |
| Синхронизация GPU и readback | `LLImageGL::syncToMainThread()` использует fence/wait; NVIDIA CPU wait происходит в worker, другие GPU получают GL wait через main queue. Снимки/некоторые picking-пути используют `glReadPixels`. Runtime occlusion probe проверяет availability; shader profiler может принудительно читать результат. | Раздельный CPU/GPU профиль и действия пользователя. Не удалять fence/wait: они защищают видимость загруженной текстуры между контекстами. Не считать все readback постоянной нагрузкой каждого кадра. |
| Периодическая диагностика | `display_stats()` пишет FPS примерно каждые 10 секунд, память по MemoryLogFrequency (600 секунд по умолчанию), asset storage каждые 60 секунд. Memory helpers обновляют сведения примерно раз в секунду. | Проверять совпадение пиков со временем операций, сравнивать с профилем без лишнего логирования. Совпадение периода само по себе не доказывает причинность. |

Не обнаружено оснований для безопасной массовой переделки renderer, изменения
значений графики по умолчанию, отключения защиты от дефицита памяти или удаления
синхронизации GL. Временные векторы с `LLPointer` защищают от удаления объектов
при callbacks; заменять их сырыми ссылками ради уменьшения аллокаций нельзя.
Статический аудит не доказывает отсутствие других утечек или гонок.

## Диагностика кадров

В Debug Settings установить `MaksFSFrameDiagnostics = TRUE`.
Вернуть `FALSE` для отключения. Параметр `Boolean`, по умолчанию `FALSE`,
`Persist=0`: после перезапуска снова выключен. Сбор начинается только при
`STATE_STARTED`; выключение/выход из этого состояния сбрасывает неполное окно.
Последнее окно короче пяти секунд при выключении не записывается.

В журнале искать категорию `MaksFSPerformance`. Одна строка после накопления
не менее пяти секунд измеренных кадров, без отдельных записей на каждый пик:

- `frames`, `slow_ge_50ms`, среднее и максимальное время измеренного кадра;
- `idle_mean_max_ms`: от существующего `frameTimer` до вызова `display()`, включая input, сообщения, idle и callbacks;
- `display_mean_max_ms`: CPU wall time вызова `display()`, включая возможные ожидания драйвера;
- `post_display_mean_max_ms`: reflection probes, snapshot updates и оставшаяся работа до фоновой стадии;
- `background_mean_max_ms`: texture/file/mesh servicing и намеренные ожидания, включая FPS limiter;
- `texture_mib`, `vertex_mib`: текущие внутренние allocation counters;
- `discard_bias`, `create_pending`, `downscale_pending`: состояние в момент записи, не максимум за окно.

Каждая пара mean/max относится к своей стадии; максимумы разных стадий могут
принадлежать разным кадрам. Нет GPU timing, percentiles, RSS или точной оценки
общего VRAM. Порог 50 ms фиксирован: при лимите 20 FPS такие кадры ожидаемы.
Сводка включает потерю фокуса, свёрнутое окно, телепорт после входа и снимки;
сравнивать следует интервалы с одинаковыми условиями. Если display пропущен,
его время и post-display равны нулю, вся работа до background учитывается в idle.

Измерение использует существующий `frameTimer`: не включает небольшой пролог
до его создания, хвост после reset, внешние паузы между `doFrame()` и запись
самой новой сводки. Следовательно, это не полное время между показами кадров.
Для end-to-end frametime использовать также существующую статистику viewer/Tracy.

Накопитель имеет фиксированный размер: два счётчика, два F64 и два массива
по четыре F64, без истории кадров и удержания ресурсов. При отключении нет
дополнительных чтений часов, GL-запросов или опросов памяти ОС. При включении
добавлены четыре чтения существующего таймера на отображаемый кадр и арифметика;
форматирование и вывод выполняются только на границе окна. Логирование само
может добавлять задержки: измерять его overhead в сравнении с выключенным режимом.

## Выполненная проверка

- `git diff --check`: пройден.
- XML настроек разобран стандартным XML-парсером; проверены парность map,
  отсутствие дублирующихся ключей и тип/default/persistence нового параметра.
- Вручную проверены точки измерения, отсутствие timer reset между ними,
  пути пропуска display, сброс неполного окна и отсутствие деления на ноль.
- Вручную проверено владение очередей: обе используют `queue<LLPointer<...>>`;
  флаг downscale доступен по тому же интерфейсу, что уже использует list processor.
- Проверены прямые объявления allocation counters и добавлены явные include.
- Компиляция C++ и runtime/GPU-проверки не выполнены: в доступной локальной среде
  нет MSVC/Clang и подготовленного дерева сборки viewer. Полная сборка для этого
  статического этапа не запускалась; изменения требуют проверки компиляцией перед merge.

## Следующая проверка на готовой среде

1. Выполнить целевую инкрементальную компиляцию затронутых translation units
   и viewer в существующем build tree; если его нет, согласовать отдельный build run.
2. Зафиксировать commit, GPU/driver, разрешение, настройки, лимит FPS, focus,
   сцену/камеру/число аватаров и состояние кэша. Сравнить основу и ветку в тех же условиях.
3. Прогреть сцену; записать несколько одинаковых интервалов по 60–120 секунд
   с диагностикой OFF, затем ON; сравнить median/p95/p99/max frametime внешним
   инструментом или существующими средствами viewer, а не только средний FPS.
4. Отдельно проверить вращение камеры, вход/телепорт, динамические probes,
   texture backlog, восстановление после memory pressure, сворачивание/возврат
   и FPS limiter. Не создавать намеренный OOM на рабочем ноутбуке.
5. Проверить выход при непустой очереди downscale и повторный вызов shutdown:
   очередь пуста, pending-флаги сброшены, нет позднего удержания текстур.
6. Проверить переключение диагностики OFF/ON, перезапуск с OFF, отсутствие
   строк при выключении и визуальные регрессии текстур/отражений.

До этих проверок PR должен оставаться draft. Вывод об устранении просадок
или гарантированном снижении потребления памяти делать нельзя.
